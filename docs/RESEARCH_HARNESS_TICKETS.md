# Tickets for the JAS research harness specification

Status: **approved for implementation; all 20 child issues published and verified**.
Parent: [spec #11](https://github.com/jaiamin/ass/issues/11).

The user requested tracer-bullet tickets, then emphasized repeated benchmarking
and iteration that strengthens generalization without breaking the platform.
GitHub is the issue tracker; this document retains the accepted breakdown.
T01–T20 identify the graph below. Each has a published child issue with native
blocking relationships. See [implementation progress](RESEARCH_HARNESS_PROGRESS.md)
for accepted checkpoints and remaining work.

## Delivery rules

- Each ticket delivers a narrow complete behavior through the existing schema,
  public workflow API, appropriate UI surface and tests. Existing UI paths may
  be reused; do not build a technical dashboard solely to satisfy a layer count.
- T01 establishes a reproducible known-source baseline before implementation.
  T02 is the first extension-risk qualification. Trusted built-in, participant,
  researcher and validity improvements need not wait for generated execution.
- Every implementation slice reruns affected inherited regressions plus its new
  behavior checks and records a source/case-stamped development comparison.
  An aggregate gain cannot erase a regression or failed attempt. Avoid repeated
  full/paid suites when new evidence does not justify them.
- Land and verify one coherent slice at a time against the last accepted
  checkpoint. Keep the existing public workflow usable throughout; a failed
  regression is repaired or recorded as blocking adoption, not hidden behind
  later features. This is incremental delivery, not a second application engine.
- Repeat relevant harness-intelligence development comparisons at researcher
  and participant checkpoints, using the same case/version and recorded effort
  envelope for before/after comparisons, plus fresh independent development
  variants. Deterministic correctness cannot establish intelligence; report
  live evidence as unverified when the necessary paid trials are unauthorized.
- Use fresh development cases during iteration. Reserve independently authored,
  frozen held-out cases for the final milestone; never silently tune/rescore
  known failed validation cases or alter published historical suites/scores.
- Preserve Pydantic AI, the Sol Researcher, Luna model-controlled participants,
  the 1–12 active-participant scope, private information, exact replay,
  immutable revisions, append-only evidence and per-request accounting.
- Existing module patterns supply the initial seams. Local policy extraction
  belongs at the start of T04; the changed world/request contract is introduced
  atomically with the real artifact-world slice in T09. No unavoidable wide
  mechanical refactor was found, so no horizontal prerequisite or legacy
  expand/contract layer is proposed.
- Runtime/container changes require the production smoke checks. Browser
  changes require appropriate keyless UI regression checks. Never weaken tests,
  change host security or spend beyond explicitly authorized allowances.
- Parent body, labels and state remain unchanged. Children were published in
  dependency order with ready-for-agent and native parent/blocking links.

https://github.com/jaiamin/ass/issues/11

### What to build

Inspect and reproduce a source-stamped end-to-end evaluation across the four agreed study families, including fresh live evidence and a held-out generated mechanic, with separate gate results and all failures retained.

### Acceptance criteria

- [ ] Freeze independent cases, rubrics, matching/sampling rationales and source identities before validation; the held-out extension task must remain outside development tuning.
- [ ] Run varied solo, three-agent information, four-agent commitment and 6–12-agent institutional cases through real public workflows; verify current UI behavior and exports in addition to deterministic mechanics.
- [ ] Require at least one genuinely absent mechanic to be generated and pass independent acceptance/privacy/replay checks; keep the milestone unpassed if none succeeds.
- [ ] Report world/isolation correctness, researcher competence, participant capability, research validity and runtime feasibility separately, preserving all attempts, repairs, missingness, costs and negative/null outcomes.
- [ ] Use separately authorized repeated Luna trials and real Sol research trials for behavioral evidence; mocks/load tests/browser demos cannot satisfy that gate. Preserve the total $10 Sol cap and prepare a concrete Luna trial manifest/estimate before requesting its separate allowance.
- [ ] Compare against the regression baseline and development checkpoints, reject unexplained regressions, and never silently tune/rescore a failed held-out trial as fresh validation.
- [ ] Keep the supported initial range at 1–12 and state remaining operating/generalization limits; this ticket neither implements large-population infrastructure nor closes or changes the parent issue.
